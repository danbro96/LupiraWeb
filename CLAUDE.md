# LupiraWeb

Personal portfolio site by Daniel Broström. The code doubles as a DevOps showcase: reproducible builds, build-time API contract, containerized dev/prod, tests across every layer.

## Architecture (current)

- **Frontend** — [lupiraweb.client/](lupiraweb.client/). Next.js 16 App Router, standalone Node runtime. Tailwind v4 (PostCSS). API client generated by Orval from a local OpenAPI spec.
- **Backend** — [src/LupiraWeb.Server/](src/LupiraWeb.Server/). .NET 10 minimal API, a **stateless BFF** over LupiraCareerApi. No database, no Marten, no EF — it reads career/résumé data from CareerApi over HTTP via a typed client ([Integration/CareerApi/](src/LupiraWeb.Server/Integration/CareerApi/)) with owner-bearer auth, and maps to public response DTOs. The DTO-supporting enums + `Location` live in [src/LupiraWeb.Server/Contracts/](src/LupiraWeb.Server/Contracts/); there are no event-sourced aggregates here. `Microsoft.AspNetCore.OpenApi` emits `/openapi/v1.json` at runtime and, via `Microsoft.Extensions.ApiDescription.Server`, writes `lupiraweb.client/backend-openapi.json` at `dotnet build`. Scalar UI mounted at `/scalar/v1` in Development. Health probes: `/livez` + `/readyz` (readiness pings CareerApi).
- **Project layout** — `src/LupiraWeb.Server/` (the BFF) + `tests/LupiraWeb.Server.UnitTests/` (DB-free; in [LupiraWeb.slnx](LupiraWeb.slnx)) + `tests/LupiraWeb.Server.IntegrationTests/` (`WebApplicationFactory` + in-process CareerApi stub; **not** in the `.slnx` — run by path). `dotnet test LupiraWeb.slnx` runs unit-only/DB-free; CI runs integration via the reusable `tests.yml`.
- **Dev proxy** — [lupiraweb.client/next.config.ts](lupiraweb.client/next.config.ts) rewrites `/api/*` to `API_BASE_URL` (default `http://localhost:5188`).
- **Containers** — [docker-compose.yml](docker-compose.yml) + [docker-compose.override.yml](docker-compose.override.yml) are **local dev only** (backend + frontend; live-mount frontend, build backend from Dockerfile, backend points at CareerApi via `CAREERAPI_BASE_URL`; no Postgres). Plain `docker compose up` auto-merges both. Production on TrueNAS runs the single stack under [deploy/](deploy/), emitting OTLP to the platform `medelynas-otel` OpenObserve — see [docs/CICD.md](docs/CICD.md).
- **Visual Studio** — [docker-compose.dcproj](docker-compose.dcproj) wraps the compose files so F5 runs the full stack in Docker with the debugger attached to the backend.

The OpenAPI contract flows **backend csproj → build-time JSON → Orval → typed client**. Changing an API endpoint means: edit the feature's endpoint class, `dotnet build`, `npm run generate:api`. The custom fetcher lives at [lupiraweb.client/src/api/fetcher.ts](lupiraweb.client/src/api/fetcher.ts) and resolves base URL based on `typeof window`.

## How to run

```bash
# Generate the OpenAPI spec + typed client
dotnet build src/LupiraWeb.Server
cd lupiraweb.client && npm ci && npm run generate:api

# Dev (two terminals)
dotnet run --project src/LupiraWeb.Server --urls http://localhost:5188
cd lupiraweb.client && npm run dev        # → http://localhost:3000

# Or via Docker (auto-merges docker-compose.yml + docker-compose.override.yml)
docker compose up --build
```

## How to test

```bash
# Backend unit + integration
dotnet test

# Frontend unit (Vitest + RTL)
cd lupiraweb.client && npm test

# Frontend e2e (Playwright — needs backend running)
cd lupiraweb.client && npm run test:e2e
```

## Working rules (for Claude)

**TDD is the default.** For any new *behavior*:
1. Write a failing test that describes the behavior.
2. Write the minimal code to make it pass.
3. Refactor with the test as a safety net.

Bug fixes get a regression test **before** the fix. Pure refactors (no behavior change) don't need new tests if coverage already exists.

Non-TDD edits are fine for: config/tooling, docs, styling-only tweaks, renames, and other work with no observable behavior change. Use judgment; if a change can break something, it needs a test.

**Other conventions:**
- Use `[file.ts:42](lupiraweb.client/src/file.ts#L42)` link format when referencing code.
- Don't introduce abstractions or "just in case" error handling beyond what the current task requires.
- No `git push`, `git reset --hard`, `git push --force`, or other destructive ops without explicit confirmation.
- Static pages are RSCs by default; `"use client"` only when the component actually uses hooks, event handlers, or browser APIs.
- Every new backend endpoint: edit the feature's endpoint class, `dotnet build` (regenerates the OpenAPI spec), `npm run generate:api`, add a test.
- lupiraweb.client stays on ESLint 9 until `npm view eslint-plugin-react peerDependencies.eslint` includes 10: `eslint-config-next` relies on that plugin, and ESLint 10 removed `context.getFilename()`.

## Backend conventions

.NET API rules (thin endpoints, `Handlers/`, `TypedResults` + `Results<...>` unions, one type per file) are in `~/.claude/CLAUDE.md`. Repo-specific:

- Repositories are thin adapters over `ICareerApiClient`: interfaces in [src/LupiraWeb.Server/Data/Repositories/](src/LupiraWeb.Server/Data/Repositories/), implementations in [src/LupiraWeb.Server/Integration/CareerApi/Repositories/](src/LupiraWeb.Server/Integration/CareerApi/Repositories/). No EF, Marten, `DbContext` or local store. Methods are intent-named (`GetByEngagementAsync`, not `Query().Where(...)`).
- OpenTelemetry via ASP.NET Core auto-instrumentation in `Program.cs` covers every endpoint; handlers do not log "entering endpoint". Dev uses the console exporter, prod OTLP via `OTEL_EXPORTER_OTLP_ENDPOINT`.

## Deployment

Production runs on TrueNAS 25.10.1 as a single `lupira-web` Custom App (backend + frontend) from [deploy/compose.yaml](deploy/compose.yaml). The backend reaches CareerApi over `medelynas_data` (or public `career-api.lupira.com`) and emits OTLP to the platform's `medelynas-otel` OpenObserve on `medelynas_telemetry`. **No database dependency** — CareerApi owns its own event store/schema. Images publish to Docker Hub as `danbro96/lupiraweb-{backend,frontend}` via [.github/workflows/release.yml](.github/workflows/release.yml). Deploys are manual (TrueNAS "Update" button); rollback is pinning `IMAGE_TAG=sha-<short>` in the App env. Full guide: [docs/CICD.md](docs/CICD.md).
